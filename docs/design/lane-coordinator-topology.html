Lane Coordinator 技术拓扑

协调器站在所有执行进程之外。它自己只有三样东西：一个纯代码的内核、一个不能执行的 Router、一本落盘的台账。干活的进程和背后的模型都可以换，台账里的任务不跟着换。

七条流

派活
你说话 → 归一 → 没人订阅 → 合批叫醒 Router → Router 提议派单 → 内核校验授权和当前状态 → 先记账 → 配包 → 投递。
上报
上报也是事件，从圆点进内核。提问和阻塞立刻转给该知道的一方，普通进展只记在任务上。停下来等人时，必须同时交一份“停下时的状态”。
要人
泳道要你拍板 → 进“待人处理” → 你定 → 直通回那个任务，同时记进决定记录。
直通
已订阅线程的新事件 → 入口检查 → 订阅表 → 配包 → 投递。不叫醒 Router，也不带来新的授权。
协同
A 的关键上报进内核 → 查订阅 → 给订阅了同一线程的 B 配包投递。包上标明来源，转发有跳数上限。
接回
你切回一件事 → 生成器从台账给你配一个包。和给泳道配包是同一个部件。
巡检
Watchdog 只读台账 → 提建议 → 进“待人处理”。它不能直接改任何东西。

任务、执行实例、授权

任务
持久。换进程、换模型、换 harness，它还是同一件事。订阅、决定和“停下时的状态”都挂在任务上。
执行实例
某一次把任务交给某个执行体。它会结束，也会被换掉。换 harness 接手叫交接，靠的是任务上的状态，不是搬运原会话。
授权范围
记在任务上，只有你能给。消息和引用的内容不能改它。要更大的范围，就开一个新任务。

有关联和没关联的任务

有关联
要共享同一份上下文才能做的事，放进一条泳道，由负责人派子执行体。只需要对方结果的事，分成两个任务，在台账里连一条边。
没关联
它们之间唯一共享的是你。要协调的是你的注意力，靠的是每个任务“停下时的状态”和接回时的上下文包。

包里的事实由程序填，叙述由模型写并且必须引用事实。导图是台账上的一个视图：上报流水是时间轴，引用边是连线。

两个可替换的接缝

执行体
一条泳道由哪个 harness 来跑。harness 自带模型，协调器不管它用哪家。
模型
只有产品自己跑的部件走模型接口，也就是 Router 和 Watchdog。它们读到的台账内容发出去之前先过外发检查。

我的选择：Router 是我们自己写的一个小循环，不是任何 harness 的会话。这样核心部件的模型才真的能换。代价是 Router 的上下文要自己管，每次醒来由生成器从台账配一份当前视图。官方原型的做法不同，它的路由层是 harness 上的一个会话。

恢复由谁负责

  • 内核用代码做机械恢复：重试没送达的投递，重启退出的执行实例。动作先记账再执行，重启后不会丢，也不会重复。
  • Watchdog 只做需要理解的判断，比如一直没进展、方向偏了。它的建议交给你，第一版不自动执行。

和官方原型的关系

文章作者公开了一个配套原型（MIT，自称研究原型）。任务和执行实例分开、授权挂在任务上、先记账再执行，这三条和它的文档一致。我们借它的模型，不用它的代码，因为它是某一个 harness 的插件。

它明说自己的命令黑名单和目录约定不是安全边界。图上泳道的橙色隔离边界要我们自己做出来并验证。

还没验证的

图上所有虚线：怎么启动一个执行体，怎么把消息送进去并叫醒它，它怎么上报。Claude Code 也在内。图里的 harness 和模型提供方都是举例。

原型只核对了文档的文字，没有对过代码。“你切走了”这件事，只有你的输入都经过交互面时内核才看得到。
