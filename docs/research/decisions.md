## 工作假设（来自落地方案，未逐条确认，可以推翻）

- **架构：** Event Kernel + Router + Worker Pool + 执行环境 + Watchdog。在 Claude Code 外面编排多个会话，不改它的内核。
- **Router 不能执行：** 不靠提示词约束，而是从工具层面拿掉执行能力。
- **直通：** 已订阅 Thread 的事件直接到 Worker，不经过 Router。
- **复用原生能力：** 用后台 Bash、subagent、hooks 和 worktree，不自建异步执行层。
- **Worker 内部：** 用 subagents，不用 agent teams（实验性，仅支持交互式）。
- **技术栈：** P0 用 Node.js/TypeScript + SQLite，Router 和 Worker 都是 `claude -p` 子进程。
- **Watchdog：** 放在主系统之外，策略变更只能提 proposal，由人合并。
- **推进方式：** 过了实验门禁才进入下一阶段。P0 第一周先跑合成负载。到“持续在线”估计 10–12 周，P0 结束时重估。

## 未决问题

1. **产品边界：只编排 Claude Code，还是跨厂商？** 11-02 的方案只考虑 Claude Code；11-04 的调研讨论了 Codex 等第三方 CLI。这会决定 Worker 接口怎么抽象，也决定 Agent Relay 是否有必要。
2. **通信层：自写还是复用？** 方案自写 Kernel，经 stdio 连接会话；11-04 的建议是不要重写通信层，先试 agentchattr，再考虑 Relay。两者还没有调和。建议（未确认）：如果只做 Claude Code，P0 先按方案自写 Kernel，试用 agentchattr 只用来判断交互形态。
3. **P0 接哪个 IM？** Slack（需要 Team/Enterprise 的 Claude Tag 或自建 app）还是 Telegram（Channels 插件，最快跑通）？方案按 Slack 写，但文档里的这条评论还没有回复。
4. **用途和合规：** 是自用、团队内部用，还是对外产品？商业条款原文还没读过，印象中有竞品和逆向工程限制（未核实）。如果对外分发，要先请法务确认。
5. **鉴权和预算：** 无人值守的会话用什么账号或 API key？月度预算上限是多少？方案里的 `--max-budget-usd 20` 只是占位值。
6. **Kernel 跑在哪里：** 方案假设一台 7×24 的小机器，而现在的开发机是 Mac。P0 是先在 Mac 上跑，还是一开始就准备常驻主机？
7. **项目命名：** 方案骨架叫 `cc-superagent/`，工作区叫 `super-agent`。
8. **泳道写的叙述能不能发给云端模型？** 拓扑 v3 里 Router 和 Watchdog 会读台账里的叙述再调模型，叙述可能带有客户材料的内容。2026-11-12 问过两次，用户还没答。答案决定模型接口的外发检查怎么做，以及 Router 能不能用云端模型。

**2026-11-12 补充：** 拓扑 v3 按“执行体可替换、Router 是自写的小循环”来画，和上面工作假设里的“Router 和 Worker 都是 `claude -p` 子进程”冲突，以拓扑 v3 为准。未决 1、2 的方向因此偏向跨厂商和自写内核，但用户只认可了大方向，没有逐条表态。官方原型的核对结果见 `dsh-superagent-prototype.md`。

**2026-11-12 再补充：** “主任务”这一条和拓扑 v3 有两处对不上，拓扑还没改。第一，台账里只有任务和执行实例，没有主任务这一层。第二，我之前假设界面只显示过了泳道边界的事、不显示对话，这个假设被推翻了。设计语言里按“主任务、任务、步”三层画，这个分法是我的理解，用户没确认。步的摘要从哪来（执行体当时上报，还是事后从对话生成）没定，和未决 8 有关。

## 动工前必须先验证

见 `super-agent-plan.md` 第 14.3 节，最影响设计的是：

- `--bare` 下 `--settings` 传入的 hooks 是否执行（Router 第三层围栏依赖它）
- `-p` 的无人值守时限对持续接收输入的子进程是否生效
- 跨会话 `SendMessage` 能否送达 `-p` 会话，以及能否按来源过滤
