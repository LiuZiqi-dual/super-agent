# 原文笔记：Exploring Super-agent Design

**来源：** [DeepSeek Harness, Exploring Super-agent Design: Towards a More Autonomous Agent System](https://x.com/DeepSeekHarness/status/2116857257245987236)，2026-11-01 发布，作者 Yujia Qiao 等。

**版本说明：** 2026-11-06 重新读取 X 页面。页面注明原文是中文，读到的是机器翻译的英文版，所以术语和具体措辞以原文为准。这里是笔记，不是全文；图表没有归档。

**定位：** 文章讨论架构思路，不是介绍 DeepSeek Harness 的现有功能。部分设计实现在 `dsh-superagent-prototype` 插件里，作者说明它只是验证原型，不是官方产品。

## 第 1 节：问题和定义

- **核心判断：** 模型已经能较少依赖人完成单任务，多任务的瓶颈变成了人的注意力。作者的经验是一个人通常只能跟进 3–5 个活跃会话。
- **现有做法的局限：** 给本地单会话 agent 加 CLI、MCP 或连接器，只能解决“收到消息”。它仍是单个同步会话，会被长操作阻塞，不同任务的上下文会混在一起，设备离线就全部停止。
- **解法：** 把 agent 从手动驱动的单个会话中解耦，变成一个跨会话保持上下文、并发推进多个任务的持续实体。
- **四个特征：**
  - **Continuous：** 在 IM、GitHub 等任何入口交互都像同一个 agent。例如 IM 里定了方案 A，PR 评论改成 B，它能跟上。
  - **Productive：** 多个复杂任务并行且质量高，上一个没完就能接下一条。
  - **Proactive：** 监听环境事件，值得处理就动手，否则保持安静。
  - **Persistent：** 始终在线，连接真实工作环境，异常后自恢复。
- **五个模块：** 两层架构、事件驱动、全双工多渠道、计算/状态/环境分离、Watchdog。作者认为单个 ReAct loop 给不了这四个特征，必须靠外围系统架构。

## 第 2 节：两层架构

连续性和吞吐量互相矛盾：所有事件进一个会话，上下文连续但吞吐低，任务细节还会互相干扰；每个事件一个新会话，吞吐高但结果割裂，多个会话分别回复也让人困惑。解法是分两层。这是逻辑分工，每层内部都不必是单个会话。

**Router 层**
- 长驻，接收所有入口的人机交互，是全局的顺序点、协调点和记忆。
- 不执行任务，只交互和派发，可以完全没有 Bash。
- 和 Agent Team 的区别：Team Lead 要理解和拆解任务，负担重；Router 只派发并跟踪任务之间的高层关系。作者的经验是 Router 的工作比预想简单，轻模型通常就够。
- 作者选了最直接的设计：单个长驻 LLM 会话。推理期间到达的事件排队，下一轮合并处理。这类请求长输入、短输出，合并的 Trigger 在 Prefill 阶段并行计算，所以请求耗时的增长远慢于批量大小。
- 真的撑不住时，可以内部多级过滤或水平分片，代价是分片越细，共享的上下文越少。

**Worker 层**
- 每个 Worker 上下文隔离、工具齐全、专注一个任务，通常用最强的模型。
- 不直接面对人，推理和工具调用不外露，只向 Router 汇报。
- Worker 之间通常不需要直接通信。冲突多发生在共享环境（如同一个 PR），只要都订阅了对应 Thread，就能收到相同事件并自行发现和解决。少数跨任务协调由 Router 转达。
- 复杂任务内部可以起 subagent 或 Agent Team，对 Router 透明。

作者认为“让用户手动管理会话”是从底层 LLM API 延续下来的设计习惯。会话应该是系统的实现细节。

## 第 3 节：事件驱动

系统的主要输入从人输入的提示词变成半结构化的环境事件（Trigger）：群消息、邮件、日历、code review 评论、CI 结果等。

**3.1 事件过滤（Fast Path / Slow Path）**
- **程序化策略：** 代码按来源、群组、用户或 bot 白名单快速判断。每个来源可配成“只响应显式请求”“作为候选事件”或“忽略”。
- **语义策略：** 候选事件交给 LLM，依据上下文和提示词写的策略决定是否行动。这一层也是自然语言扩展点，人可以随时用提示词增删策略。

**3.2 事件路由**
- 同一 PR、IM 话题或邮件链的连续事件组成 Thread。
- Router 为 Thread 的首个事件创建 Worker，Worker 直接订阅该 Thread。
- **已订阅：** 代码把后续事件直通 Worker。超出任务范围时，Worker 可以退订或退回给 Router。
- **未订阅：** Router 能看到每个事件以掌握全局，但只评估和派发还没有订阅者的新事件。
- 订阅是多对多的，共享 Thread 的新事件会同时送达所有订阅者。

**3.3 上下文组织**
- 把上下文窗口当缓存。Inline 把马上要用的放进窗口，Spill 把超预算或少用的放到窗口外，只留引用或摘要。
- 利用局部性逐步内联：先给当前对象的 ID 和摘要，再给紧密相关对象的 ID，再给时空相邻的内容（例如内容前 50 字符、前后 IM 消息、被回复的消息、同一 review 的相邻评论）。
- 超长内容截断并留指针，需要时用工具读取。
- **Chain of Recall：** Trigger、Thread、Worker Session 都有唯一 ID，组成引用图。每次 recall 的结果也遵守 Inline & Spill，内联下一跳的摘要和 ID，模型可以一跳一跳地找回上下文。

**3.4 Acting Ahead（投机执行）**
- 依据环境信号在后台先开工，用额外算力减少人的等待和介入。有用就交付，没用就丢弃。
- 例子：内部用户群配置了“静默复现并修复”策略。有人报问题时，agent 先在后台尝试复现和修复；只有确认问题并找到简单修复后才交付，否则全程不说话。

## 第 4 节：全双工多渠道

- **全双工：** 经典 ReAct 的同步调用会阻塞循环。改成异步 `start()` / `stop()`：`start()` 立即返回“已启动”，工具完成后结果作为新事件送回，模型也能主动停掉跑太久的命令。文章说 DeepSeek Harness 已实现，但还没有默认开启。
- **IM 类渠道：** 轻量、少打扰。只在需要决定或签字时通知，只问直接问题，给简短结论。文章验证过的硬规则是每条回复不超过 100 词。
- **GitHub、邮件、文档：** 结构化、信息密度高。例如 PR 按项目惯例写全问题背景、改动说明和验证结果。

> 注意：对话 1 的摘要把上限写成“≤100 字”，原文（英文版）是 100 words。落地方案写的是“100 英文词 / 150 汉字”，其中 150 汉字是我们自己折算的，不是原文数字。

## 第 5 节：计算、状态、环境分离

- **计算和状态分离：** Agent Loop 跑在无状态弹性容器里，会话等持久状态放在数据库。本地设备休眠不影响 agent。
- **计算和环境分离：** 真实环境包含未提交的改动、私有凭据、内网依赖和特定硬件，同步到云端成本高且容易遗漏。所以环境留在原地，端点只放一个轻量 daemon，不存会话状态，只负责执行命令和返回结果。
- **BYOM：** 支持接入用户自己的开发机，也支持云主机和按需创建的环境。设备重新上线时，云端 agent 会自动启动并完成需要在该设备上跑的任务。
- 文章提到 Anthropic 的《Decoupling the brain from the hands》思路相同，区别是那篇主要讲托管服务的按需沙箱和客户 VPC 资源，这篇先解决个人机器的接入。

## 第 6 节：Watchdog

- 持续在线的系统不能只靠内部逻辑，需要主系统之外的独立控制环。
- 很多异常不是崩溃：进程还在跑，但模型在原地打转或偏离目标，所以要监控任务进度，不只是存活。
- 实现是一个由定时消息驱动的独立 Watchdog Session：处理 API 错误、状态恢复失败等基础设施故障，并用模型判断 Worker 是否有实质进展、是否偏离目标。
- 它有完整工具，维护者可以用自然语言问它为什么失败，也可以让它在运行中调整主系统（例如增删提示词、改触发规则）。

> 落地方案在这里有意和原文不同：Watchdog 读的是不可信转录，所以只能提 proposal，不能直接改策略。见 `plan-merge-review.md`。

## 第 7 节：初步实验

作者明确说实验用的是合成负载和简化环境，部分设置可以更严格，结果仅供参考。

**7.1 四种设计的消融实验**
- **负载：** 群聊和 GitHub CI 消息流，每次约 300 条，其中约 20 条是工作请求，其余是闲聊、追问、取消和 CI 消息。
- **模拟方式：** 编码工作用一个只消耗时间的工具模拟，所以测的是调度协调，不是单任务能力。消息间隔和工作时长按 1/4 缩放，模型调用时间不缩放。每种设计跑 5 次。

| 设计 | 完成时间 p50 / p95（分钟） | 每次运行 cache-read token |
| --- | --- | --- |
| Super-agent | 12.4 / 15.7 | 23.2M |
| Super-agent，无直通 | 12.6 / 15.5 | 31.8M |
| 单会话 + subagent，中性提示 | 20.4 / 29.5 | 6.1M |
| 单会话 + subagent，委派优先提示 | 13.8 / 29.0 | 10.8M |

- **中性提示：** 5 次运行都没有调用 subagent，所有工作都在主会话里做，不断被新消息打断。
- **委派优先提示：** 5 次中有 4 次委派。剩下 1 次模型判断工作“很小”就自己做了，造成长尾。
- **直通的作用：** 不让任务更快或更好，但去掉后 Router 决策约多 30%，总 cache-read token 约多 37%。
- **代价：** Super-agent 用更多 token 换更短、更稳定的完成时间。

**7.2 Router 合批压测**（Router 用真实模型，Worker 用 mock 模型）

| 指标 | 约 1 个/分钟 | 约 40 个/分钟 |
| --- | --- | --- |
| 平均批大小 | 1.0 | 2.8 |
| 单次请求耗时 | 2.5 秒 | 3.9 秒 |
| 均摊每个决策的推理时间 | 6.4 秒 | 1.6 秒 |

一次决策可能跨多个 LLM 请求，所以决策耗时可以大于请求耗时。作者据此认为，以他们目前的团队规模，不必提前分片。

## 第 8 节：开放问题

- **8.1 扩展：** 什么时候分片 Router、分多细，Worker 什么时候需要直接通信，都没有定论。可以考虑针对 Router 工作训练模型。运行数月后，长期记忆会成为主要瓶颈。
- **8.2 无会话的交互：** 如何呈现任务、如何让人中途介入或接管，仍待探索。作者认为最终设计会高度定制。
- **8.3 上下文边界和 A2A：** 如何划分实例，本质上是决定哪些上下文共享、哪些隔离。不共享上下文、权限边界不同的 agent 之间如何安全协作，还没有解决。
- **8.4 安全和隐私：** 事件驱动带来更多不可信输入。云端 Agent Loop 一旦被入侵或注入，所有连接的端点都可能被接管。凭据只要能进入模型上下文，正常运行时也可能泄漏，所以 agent 要能使用凭据但看不见凭据。作者的结论是，这些问题不解决，Super-agent 只能在很小的信任范围内使用。

## 读这篇文章时要注意

以下是整理时的 **[判断]**：

- 实验不能证明任务质量更好，因为编码工作是 mock 的。
- 负载是作者构造的，作者的团队规模也没有给出具体数字，所以“不必分片”不能直接套用到其他规模。
- 文章来自同样在做这类系统的团队，是设计主张加初步数据，不是独立评估。这也是落地方案要求 P0 先自己复现实验的原因。
